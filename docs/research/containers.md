## 1. Виды файлов и как их различать (сигнатуры и элементы контейнера)

### 1.1. Все четыре расширения — это один и тот же «контейнер 1C:V8»

`.cf`, `.cfe`, `.epf`, `.erf` (а также `.cfu`) — каталог файлов (FAT + блоки). Различий в
физическом формате между ними **нет**, различается только *набор элементов* и *содержимое*.

Формат 1.5 (8.0–8.3.15):
- Заголовок файла 16 байт: `start_empty(int32)`, `page_size(int32)`, `version(int32)`, `0`
  (`APIcfBase.h:69-75`, `APIcfBase.cpp:1256-1261`).
- Таблица размещения (FAT) лежит по смещению 16, элемент 12 байт: `header_start`, `data_start`,
  `0x7fffffff` (`APIcfBase.h:53-58`, `APIcfBase.cpp:1280-1295`), количество файлов = `fat.Size / 12`
  (`APIcfBase.cpp:1282`).
- Заголовок блока — 31 байт текста `"\r\n%08x %08x %08x \r\n"`:
  `[2]` — полная длина данных, `[11]` — длина в текущей странице, `[20]` — адрес следующей страницы
  (`APIcfBase.cpp:12`, `APIcfBase.cpp:82-124`), конец цепочки — `0x7fffffff` (`v8_constants.h:12`).
- Заголовок элемента: 8 байт `time_create`, 8 байт `time_modify`, 4 нуля, имя в UTF-16LE, 4 нуля
  (`APIcfBase.cpp:1300-1307`; те же поля в `V8File.h:291-302`).

Формат 1.6 (8.3.16+):
- Заголовок 20 байт, элементы FAT по 24 байта, заголовки блоков 55 байт (`APIcfBase.h:61-84`,
  `APIcfBase.cpp:128-170`, `V8File.h:174-231`).
- Признак — 8 байт `0xFF` по «магическому» смещению `0x1359` = 4953
  (`v8_constants.h:17-19`; проверка `APIcfBase.cpp:953-972`; смещение при чтении блоков
  `APIcfBase.cpp:158`, `V8File.h:250-262`).
- Именно поэтому наш CLI для `1Cv8_bp.cf` печатает «формат 1.6», а для `.epf/.cfe` — «1.5»:
  различие только в контейнере, текстовые структуры внутри одинаковые.

Данные элементов:
- Для `.cf/.epf/.erf/.cfe` элементы **сжаты deflate**; флаг выставляется по расширению
  (`APIcfBase.cpp:1071`: `zipped = ext == str_cf || ext == str_epf || ext == str_erf || ext == str_cfe`),
  распаковка при чтении — `APIcfBase.cpp:1537-1542`.
- `.cfu` — единственное реальное отличие на уровне контейнера: весь файл — один deflate-поток,
  после распаковки это обычный контейнер 1.5 (`APIcfBase.cpp:1052-1068`).
- Определение «это контейнер» — эмпирическое: длина 16 + сигнатура пустого каталога
  (`APIcfBase.cpp:13`) либо проверка символов `\r\n` и пробелов в заголовках блоков по смещениям
  0 и 16 (`APIcfBase.cpp:975-1042`, `APIcfBase.cpp:512-597`).

### 1.2. Набор элементов контейнера по типам (проверено на реальных файлах)

| Тип | Элементы верхнего уровня | Пример |
|---|---|---|
| `.cf` (8.1–8.3) | `root` (44 Б), `version` (30 Б), `versions` (большой), далее `N` файлов с именами-GUID | `1Cv8_bp.cf`: `root`=44, `version`=30, `versions`=6 073 860 |
| `.cf` (8.0) | `root`, `version`, `metadata` (каталог), `versions` | `MainUnit.cpp:1718-1735` |
| `.epf` / `.erf` | `root` (44 Б), `version` (30 Б), `versions`, **`copyinfo`**, далее файлы-GUID | `UI_Portable.epf`: `copyinfo`=3044; `bddRunner.epf`: `copyinfo`=25942 |
| `.cfe` | **только `configinfo`** + файлы-GUID; `root/version/versions` **отсутствуют** | `YellowWatcher.cfe`: `configinfo`=16 701 |
| `.cfu` | deflate-обёртка контейнера 1.5 | `APIcfBase.cpp:1052-1068` |

Содержимое служебных элементов:

```
root     = {2,<GUID корневого объекта>,}                 // .cf, .epf, .erf  (44 Б)
version  = {{216,0,{<номер>,0}}}                          // 30 Б, 216 — маркер «новый формат»
versions = {1,<N+1>,"",<uid>,"<имя файла>",<uid>, ... }   // пары имя→uid версии
copyinfo = {4,{N,{uid,uid,1,{ClassId,"Имя"}},...},{M,{uid,uid,флаг},...},...}
```

- `version`: `MainUnit.cpp:1699-1716` разбирает `node[0][0][0]` и получает `216`; `ver < 100`
  означает формат 8.0 и наличие каталога `metadata` (`MainUnit.cpp:1718-1735`).
- `versions`: `{1, count, "", uid, "<name>", uid, ...}`. Проверено: `1Cv8_bp.cf` — `{1,78845,...}`
  при 78 844 элементах; `UI_Portable.epf` — `{1,285,...}` при 284 элементах, т.е. **count = элементов + 1**
  (дополнительная пара с пустым именем — версия «самого контейнера»). Шаблон в эталоне:
  `guids.h:1592` (`_versions_`), `guids.h:1581-1590` (`_root_`, `_version_`).
- `copyinfo`: список внутренних объектов внешней обработки с их `ClassId` и именем, плюс список
  связей «объект→родитель». В нашем коде не используется, в эталоне — тоже (см. 2.1).
- `versions` эталон **фактически не читает**: константы `file_versions`/`CFileNameVersions`
  объявлены (`guids.h:1566`, `guids.h:1571`), но нигде не используются; читаются только литералы
  `L"version"` (`MainUnit.cpp:1692`) и `L"root"` (`MainUnit.cpp:1742`).

### 1.3. Как определить тип файла по содержимому (надёжнее расширения)

1. Есть элемент `configinfo` → **расширение `.cfe`** (проверено: `root/version/versions` в `.cfe` нет).
2. Есть `root` + `version` + `versions` + `copyinfo`, а файл по `root` — «обёртка»
   `{1,{guid},1,{ClassId,body}}` → **`.epf`/`.erf`**.
3. Есть `root` + `version` (+ `metadata` для 8.0), файл по `root` — `{2,{guid},N,{ClassId,child}...}`
   с таблицами классов метаданных (`bf845118…`, `cf4abea6…`, `631b75a0…`) → **`.cf`**.
4. Файл не открывается как контейнер, но после inflate открывается → **`.cfu`**
   (`APIcfBase.cpp:1052-1068`).

### 1.4. Где эталон выбирает режим открытия (и чего он не делает)

- Единственное место, где эталон смотрит на расширение, — конструктор каталога:
  `APIcfBase.cpp:1051` (`ExtractFileExt`), `APIcfBase.cpp:1052` (`cfu`), `APIcfBase.cpp:1071`
  (флаг `zipped` для `cf/epf/erf/cfe`). Дальше по коду тип файла нигде не используется:
  `grep -i cfe` даёт только `APIcfBase.h:23,30`, `APIcfBase.cpp:1071`, комментарий `ConfigStorage.h:57`;
  `configinfo` встречается только в `ConfigStorage.cpp` (это таблицы ИБ, см. §3.4);
  `copyinfo` не встречается вообще.
- Открытие из GUI: `MainUnit.cpp:1400-1535` (`ActionFileOpenExecute`), ключевая строка —
  `MainUnit.cpp:1477`: `GlobalCF = std::make_unique<v8catalog>(filename, true);` — контейнер всегда

  (`MainUnit.dfm`, `object dlgOpenCF: TOpenDialog` — свойство `Filter` не задано).
- Далее всегда вызывается один и тот же разбор конфигурации: `MainUnit.cpp:1481`

- **Итог:** отдельного режима «epf/erf/cfe/хранилище» в эталоне нет. Для `.epf/.erf` поиск таблиц
  классов ничего не находит, а затем разбор идёт по путям свойств конфигурации

  То есть эталон **не отображает состав `.epf/.erf`**, хотя контейнер открывает.

## 2. `.epf` / `.erf`: структура, корневой объект, отличия от `.cf`, состав и модули

### 2.1. Контейнер

Верхний уровень — как в §1.2. Корневая ссылка одинакова с `.cf`:

```
root = {2,433e4fdb-ede4-4263-bd7b-a306d3fac8f9,}    // UI_Portable.epf
root = {2,c15bf2f2-272d-4fe6-a321-0d77e353c1ab,}    // bddRunner.epf
```

Разбор — как `MainUnit.cpp:1742-1768`: `root[0][1]` = GUID файла метаданных корневого объекта,
затем `cat->GetFile(meta)`.

### 2.2. Корневой объект `.epf` — «обёртка с одним объектом»

Файл `<root-GUID>` (в `UI_Portable.epf` — элемент №91, 5817 байт; в `bddRunner.epf` — элемент №20,
51 772 байта) имеет вид:

```
{1,                          // маркер контейнера метаданных («1» — один/внешний объект)
 {<GUID файла>},             // self-ссылка (совпадает с именем элемента)
 1,                          // число дочерних объектов
 {<ClassId>,                 // для внешней обработки: c3831ec8-d8d5-4f93-8a22-f9bfae07327f
  {1, <свойства>, M, <таблицы>...}   // тело объекта — та же структура, что у объекта .cf
 }
}
```

- `c3831ec8-d8d5-4f93-8a22-f9bfae07327f` — ClassId `ExternalDataProcessor` (внешняя обработка);
  это подтверждается и `copyinfo` (объект `72a612b7…` имеет ClassId `c3831ec8…`), и внешними
  источниками по XML-дампу метаданных: `MetaDataObject/ExternalDataProcessor` →
  `<xr:ClassId>c3831ec8-d8d5-4f93-8a22-f9bfae07327f</xr:ClassId>`
  ([пример XML](https://gitlab.rarus.ru/dr-1C-retail/oneterminal/-/raw/947f39e08c53584f1e024eb91419e46427c0fb72/epf/%D0%A3%D1%81%D1%82%D0%B0%D0%BD%D0%BE%D0%B2%D0%B8%D1%82%D1%8C%D0%97%D0%B0%D0%B3%D0%BE%D0%BB%D0%BE%D0%B2%D0%BE%D0%BA%D0%9E%D1%82%D1%87%D0%B5%D1%82%D0%B0%D0%9F%D0%BE%D0%A5%D1%80%D0%B0%D0%BD%D0%B8%D0%BB%D0%B8%D1%89%D1%83.xml),
  [описание ClassId для EPF](https://claudskills.com/skills/epf-expert/SKILL.md)).
- Свойства внешней обработки (`<свойства>`) — список из 7 элементов:

```
{4, <guidA>, <guidB>,
   {0,{N,{1,0,<ObjectUID>},"<Имя>",{K,"ru","<Синоним>",...},"<Комментарий>",...}},
   <GUID формы по умолчанию>, "",
   <GUID модуля объекта | 00000000-…>}
```

Проверено:
- `UI_Portable.epf`: `{4,9f4fe7f4-…,95e39d8f-…,{0,{3,{1,0,72a612b7-…},"УИ_ПортативныеУниверсальныеИнструменты",{1,"ru","Портативные универсальные инструменты"},"26.5.1",0,0,00000000-…,0}},4cb820fd-…,"",00000000-…}`
- `bddRunner.epf`: `{4,b5f066dc-…,5202445a-…,{0,{1,{0,0,fcd4c9b7-…},"bddRunner",{20,"ru","Vanessa ADD",…},"https://github.com/vanessa-opensource/add",0,0}},8a6e31ea-…,"",813effc7-…}`

Важно: **`ObjectUID` внутри дескриптора ≠ имя файла** (`UI`: файл `433e4fdb…`, UID `72a612b7…`;
`bdd`: файл `c15bf2f2…`, UID `fcd4c9b7…`). Это критично для поиска модулей (см. 2.4).

### 2.3. Чем `.epf` отличается от `.cf` (структурно)

| Признак | `.cf` (конфигурация) | `.epf`/`.erf` |
|---|---|---|
| Элементы контейнера | `root`,`version`,`versions` (+`metadata` в 8.0) | + `copyinfo` |
| Корневой объект (`{2,guid,…}`) | `{2,{guid},N,{ClassId,body}…}` — контейнер из N дочерних объектов; для конфигурации N=7 | `{1,{guid},1,{ClassId,body}}` — ровно 1 дочерний объект |
| Маркер первого элемента | `2` (проверено на `1Cv8_bp.cf`) | `1` |
| Дочерние ClassId корня | `9cd510cd…` («Configuration»), `9fcd25a0…` («Метаданные», внутри — 15 таблиц-классов), `e3687481…`, `9de14907…`, `51f2d5d8…`, `e68182ea…`, `fb282519…` + завершающий `{{0,"",""}}` | `c3831ec8…` (ExternalDataProcessor) |
| Таблицы классов (`bf845118… Обработки`, `cf4abea6… Справочники`, `631b75a0… Отчеты`, …) | есть; лежат в дочерних объектах корневого объекта (в т.ч. в «Метаданные» `9fcd25a0…`, 15 таблиц) и находятся рекурсивным поиском (`Parse_tree.cpp:1148-1190`, `MainUnit.cpp:2029-2063`) | **нет** — поэтому `fill_md` эталона ничего не находит |
| Имя/синоним/версия | свойства объекта «Configuration»: `props[15]` — версия конфигурации (`MainUnit.cpp:3080`), синоним — `props[1][1][3]` (`MainUnit.cpp:3044,3068-3077`) | свойства — 7 элементов (см. 2.2), версия конфигурации отсутствует |

Файл обычного объекта `.cf` (справочник, обработка, документ) — это уже
`{1, <свойства>, M, <таблицы>…}`, то есть **тело** объекта `.epf` структурно совпадает с объектом
конфигурации; у `.epf` добавляется только внешняя обёртка `{1,{guid},1,{ClassId,body}}`.
Это подтверждено сравнением дампов: `cf_dataproc1.txt` (объект «Обработка» из `1Cv8_bp.cf` —
`{1,{17,…},5,{таблицы}}`) и `epf_rootobj.txt` (тело — `{1,{4,…},4,{таблицы}}`).

Порядок таблиц тоже разный (нельзя полагаться на индексы):

|---|---|---|
| `2bcef0d1-0981-11d6-b9b8-0050bae0a95d` — табличные части | 3 | 3 |
| `3daea016-69b7-4ed4-9453-127911372fe6` — макеты (`guids.h:161`) | 4 | 4 |
| `45556acb-826a-4f73-898a-6025fc9536e1` — команды | 5 | **отсутствует** |
| `d5b0e5ed-256d-401c-9c36-f630cafd8a62` — формы (`guids.h:1539`) | 6 | 5 |
| `ec6bb5e5-b7a8-4d75-bec9-658107a699cf` — реквизиты | 7 | 6 |

Для других классов объектов порядок свой вообще (`Catalogs.cpp:10-24`: макеты 3, команды 4,

### 2.4. Что нужно, чтобы отобразить имя, состав и модули `.epf/.erf`

1. `root` → `{2, RootGUID}` (`MainUnit.cpp:1742-1768`).
2. Элемент `RootGUID` → `{1,{self},1,{ClassId, Body}}`; проверить ClassId (для `.erf` — ClassId
   внешнего отчёта, см. 2.6).
3. `Body = {1, <props>, M, <tables>}`.
4. Имя/синоним/комментарий — из дескриптора `props[3][1] = {N,{flag,0,UID},"Имя",{K,"ru","Синоним"},
   "Комментарий",…}`: имя `[2]`, синоним `[3]` (список пар «язык,текст»),
   комментарий `[4]`. Аналогичная навигация по синониму — `MainUnit.cpp:3044-3077`,
   по имени — `MainUnit.cpp:3062`.
5. Состав — по таблицам-`GUID` (см. таблицу выше) + макеты/формы/команды/реквизиты:
   - реквизиты: элементы — записи вида `{{0,{27,{2,{3,{1,0,guid},"Имя",…}}}},0}`,
     путь к имени `{0,1,1,1,2}` (`MetadataObjectWithSections.cpp:14`, `DataProcessors.cpp:14`);
   - команды: путь к имени `{0,1,2,9,2}` (`DataProcessors.cpp:19`), GUID — первый GUID в записи
     (`MetadataObjectWithSections.cpp:20-37,186`);
   - табличные части: путь `{0,1,5,1,2}`, GUID табличной части — `{0,1,5,1,1}`
     (`MetadataObjectWithSections.cpp:131,136`);
   - формы и макеты — элементы таблицы являются GUID-ссылками на отдельные файлы контейнера;
     имена читаются из этих файлов:
     формы — `{0,1,1,1,1,2}` (`Common.cpp:477-480`, `GetNameFormReports`),
     макеты — `{0,1,2,2}` (`Common.cpp:533-536`, `GetNameMoxCatalogs`),
     чтение объекта по GUID — `BaseMetadataObject.cpp:17-31` (`get_treeFromV8file(parent->GetFile(guid))`).
   - Проверено на `UI_Portable.epf`: `props[4]` = `4cb820fd…`, и именно `4cb820fd…` — первый элемент
     таблицы форм `d5b0e5ed…` (32 элемента) → это форма «по умолчанию».
6. Модули. Модуль объекта/формы лежит в отдельном элементе-контейнере
   `<UID>.<N>` (`N` = 0,1,2,…), который сам является контейнером 1.5 с файлами `info` (15 Б) и
   `text` (исходник модуля):
   - эталон: список кандидатов `<guid>.0 … .5` + сам `guid` (`ModuleTextStorage.cpp:110-136`),
     чтение вложенного каталога, файлы `text`/`module`, затем любой дочерний с «text»/«module» в имени,
     затем «текст внутри метаданных» (`ModuleTextStorage.cpp:360-413`);
   - `TryLoadFromSourceCfByGuid` — то же по распакованному каталогу `SourceCF`
     (`ModuleTextStorage.cpp:183-260`), `LoadByMetadataObject` добавляет GUID-ы, найденные в
     метаданных объекта (`ModuleTextStorage.cpp:591-643`);
   - проверено: `UI_Portable.epf` → элемент `72a612b7-…0` = контейнер `{info, text}`,
     `text` = 36 845 Б кода; `bddRunner.epf` → `fcd4c9b7-…0` = `{info,text}` 143 465 Б;
   - **префикс — `ObjectUID` из дескриптора**, а не имя файла: `<RootGUID>.0` в `.epf` нет.
   - для объекта обычной `.cf` префикс совпадает с именем файла (например, обработка
     `67f2c151…` → элемент `67f2c151-….2` = `{info,text}` 37 030 Б; суффикс зависит от вида модуля
     и версии: встречаются `.0… .5` и даже `.a… .c`, у корневого объекта конфигурации — `.0… .c`).
   - Итоговое правило: перебирать `<UID>.<0…5>` (и, при необходимости, hex-суффиксы `a…f`),
     принимать только содержимое, похожее на модуль 1С (`ModuleTextStorage.cpp:461-470`).

## 3. `.cfe` (расширение конфигурации)

### 3.1. Контейнер

В `YellowWatcher.cfe` — 215 элементов: `configinfo` (16 701 Б) + 214 файла-GUID
(`031f4f84…`, `031f4f84….0`, …, `fd9fb905….0`). Элементов `root`, `version`, `versions` **нет**.
Проверено: `build\v8reader_cli.exe dump <cfe> root` → «Элемент «root» не найден».

### 3.2. Структура `configinfo`

`configinfo` — не один список, а **поток из трёх значений 1С**, разделённых запятыми
(файл начинается с `{0,` без внешней скобки). Эталонный парсер `parse_1Cstream`
(`Parse_tree.cpp:378-402`) создаёт синтетический корень, дети которого — значения потока
(то же делает `parse_1Ctext`, `Parse_tree.cpp:635-658`; `get_treeFromV8file` —
`Class_1CD.cpp:196-240`).

Разбор эталоном (`ConfigStorage.cpp:1071-1104`): `tt->get_first()`, затем `.get_next()` дважды,
затем `.get_first()` — то есть берётся **третье** значение, у него первый ребёнок — счётчик.
Проверено на нашем дампе (`cfe_configinfo.txt`):

```
значение[0] = {0,{216,0,{80315,0}}}                      // дескриптор/версия: 216 — маркер, 80315 — число версии
значение[1] = {2,0486e422-ae70-44b4-8b58-e7952ce247b8,<base64 ~1934 симв.>}
                                                          // корневая ссылка, как _root_ (guids.h:1581-1583)
значение[2] = {214,"<имя файла>","<base64 20 байт>", …}   // 429 элементов = 1 + 2*214: карта имя→хэш
```

Детали:
- `значение[1][1]` = **GUID корневого объекта расширения** (`0486e422-ae70-44b4-8b58-e7952ce247b8`),
  и в контейнере действительно есть элемент с этим именем (8651 Б, `cfe_rootobj.txt`).
- `значение[1][2]` — base64 длиной 1934 символа → 1328 байт; **не deflate и не zlib** (проверено:
  `deflate/zlib decode failed`). Это непрозрачный бинарный блок свойств (аналог base64 в `_root_`,
  `guids.h:1581-1583`); для отображения не нужен.
- `значение[2]` — карта «имя файла → SHA-1 содержимого»: base64 декодируется в **20 байт**.
  Проверено на элементе `031f4f84-60ed-4348-9487-8bcdb9b46209`: base64 `1Wq0soKY0nTrHrJ1G52OsDQXzcs=`
  совпадает с SHA-1 **хранимых (сжатых) байт** элемента (174 Б raw), а не с распакованным текстом
  (298 Б; SHA-1 не совпадает). Хэши — целостность/дедупликация, для чтения состава не нужны.
- `214` хэшей = 215 элементов минус сам `configinfo`.

### 3.3. Корневой объект расширения

`0486e422-…` (8651 Б) — это **конфигурационный** объект, ровно как корень `.cf`:

```
  {9fcd25a0-…, {6,{1,{1,0,533cdb66-…},00000000-…},15, …}},  // «Метаданные»: 15 таблиц классов
  {e3687481-…,…}, {9de14907-…,…}, {51f2d5d8-…,…}, {e68182ea-…,…}, {fb282519-…,…},
```

Внутри есть таблицы классов метаданных (путь `root[4][1][1][…]`, секция «Метаданные»), проверено:


Глобальные разделы (общие модули, роли, подсистемы и т.п.) лежат в первом дочернем объекте

найти корневой GUID (из `configinfo`, а не из `root`).

### 3.4. Поддержка `.cfe` в эталоне

- **Standalone `.cfe` не поддерживается вообще**: `configinfo` упоминается только в
  `ConfigStorage.cpp` в контексте таблиц ИБ `CONFIGCAS` / `CONFIGCASSAVE`
  (`Class_1CD.cpp:8032-8033`, `ConfigStorage.h:146-165`), а не файла `.cfe`.
- Что есть в этих классах (единственный разбор `configinfo` в эталоне):
  `ConfigStorageTableConfigCas` (`ConfigStorage.cpp:1032-1169`) — читает `configinfo` из таблицы
  `CONFIGCAS` по имени версии (`ConfigStorage.cpp:1050-1063`), разбирает поток
  (`ConfigStorage.cpp:1071-1104`), затем для каждой пары «имя, base64» декодирует base64
  (`ConfigStorage.cpp:1144`, `Base64.h:9-11`) и получает имя файла `hexstring(stream)`
  (`ConfigStorage.cpp:1146-1153`; `Common.cpp:425`), по которому ищет файл в таблице
  (`ConfigStorage.cpp:1148`). `ConfigStorageTableConfigCasSave` (`ConfigStorage.cpp:1181-1354`)
  отличается тем, что файлы называются `<GUID расширения>__<имя>` (`ConfigStorage.cpp:1205-1243`).
- Вызовы: `T_1CD::save_config_ext` / `save_config_ext_db` (`Class_1CD.cpp:11911-11935`) —
  сохранение расширения из ИБ в файл.
- Зацепки, которые эталон даёт для реализации `.cfe`: структура `configinfo` (см. 3.2), GUID
  корневого объекта (`значение[1][1]`), таблицы классов в корневом объекте (3.3), байтовый
  base64-блок свойств (игнорировать).

### 3.5. Что нужно реализовать для `.cfe`

1. Парсить `configinfo` как поток значений (3 значения) — не как один список.
2. `RootGUID = значение[1][1]`; открыть элемент `RootGUID`.
3. Разобрать корневой объект как `.cf` (`{2,{guid},N,{ClassId,child}…}`) и собрать состав по
   таблицам классов (`bf845118…`, `cf4abea6…`, `631b75a0…` и т.д. — см. `guids.h:110-161`).
4. Имя/синоним/комментарий/версию расширения — из свойств «Configuration»
   (`props[1][1][2]`, `props[1][1][3]`, `props[15]` — как `MainUnit.cpp:3044-3080`) либо из
   `configinfo[0]` (`80315`).
5. `configinfo[2]` (SHA-1) — опционально, для проверки целостности; на состав не влияет.
6. Учесть, что у расширения может не быть объектов (пустые таблицы классов) — это нормально.

## 4. «Хранилище конфигурации»: формат каталога и API эталона

### 4.1. Терминологическая развилка

В эталоне есть два разных «хранилища»:

1. **Каталог распакованной конфигурации** (адаптер `ConfigStorageDirectory`, `ConfigStorage.h:41-54`,
   `ConfigStorage.cpp:30-93`) и распакованные исходники `SourceCF` — это **каталог**, где имена
   файлов/каталогов = имена элементов контейнера (GUID), а тексты модулей лежат в
   `<GUID>.<N>/text`.
2. **Настоящее «хранилище конфигурации» 1С** — это **не каталог, а 1CD-подобная БД** с таблицами
   `DEPOT`, `VERSIONS`, `HISTORY`, `EXTERNALS`. Эталон определяет её по наличию таблицы `DEPOT`
   (`Class_1CD.cpp:8036`, `Class_1CD.cpp:8071-8078`), читает версии
   (`Class_1CD.cpp:10004-10059`, `get_ver_depot_config(0/-1/...)`) и выгружает в `.cf`
   (`save_depot_config` — `Class_1CD.cpp:10112`, `save_part_depot_config` —
   `Class_1CD.cpp:10941`).

Ниже описаны оба, так как в задании «хранилище» упомянуто как каталог, но в реальном 1С это БД.

Важное замечание по коду эталона: классы `ConfigStorageDirectory` (`ConfigStorage.h:41-54`) и
`ConfigStorageCFFile` (`ConfigStorage.h:57-71`) **объявлены и реализованы, но в текущем коде нигде
не инстанцируются** (используются только `ConfigStorageTable*` — `Class_1CD.cpp:8121,8129,11916,11929`).
Это «наследие» от v8unpack; для нас они — готовый образец API, а не рабочий путь чтения.

### 4.2. Каталог (распакованная конфигурация / `SourceCF`)

Создание каталога:
- `v8unpack::Parse(file, dir, filter)` (`V8File.cpp:963-975`) → `recursive_unpack`
  (`V8File.cpp:550-613`): для каждого элемента создаётся путь `dir/<ElemName>`;
  если данные элемента сами являются контейнером, рекурсия (`SmartUnpack`, `V8File.cpp:531-543`),
  иначе пишется файл; при распаковке конфигурации данные предварительно inflate
  (`MainUnit.cpp:565-586` — `StartConfigUnpackThread` → `v8unpack::Parse(..., SourceCF, {})`).
- Сборка обратно: `v8unpack::BuildCfFile` (`MainUnit.cpp:3428`, `V8File.h:325-329`);
  упрощённый аналог — `v8catalog::SaveToDir` (`APIcfBase.cpp:1868-1887`).

Имена и структура:
- Верхний уровень: `root`, `version`, `versions`, `configinfo`, затем файлы/каталоги с именами
  GUID (`031f4f84-…`, `031f4f84-….0`, …) — ровно имена элементов контейнера.
- Вложенный контейнер становится **каталогом** с теми же именами детей: например
  `72a612b7-….0/` содержит `info` и `text` (модуль объекта), `<форма>.0/` — `form` и `module`.
- **Тексты модулей**: `SourceCF/<GUID>.<N>/text` (эталон читает именно так:
  `ModuleTextStorage.cpp:199-220`, `TPath::Combine(containerPath, L"text")`;
  запасной вариант — `.../module`, `ModuleTextStorage.cpp:219`;
  то же в `MainUnit.cpp:376-397`).
- Формат 1.6 (8.3.16+) при распаковке даёт ту же схему; смещение 0x1359 учитывается в
  `V8File.h:250-262` (`Format16::BASE_OFFSET`).

API каталога (`ConfigStorage.h:28-38` — виртуальный интерфейс):
```cpp
virtual ConfigFile* readfile(const String& path) = 0;
virtual bool        writefile(const String& path, TStream* str) = 0;
virtual String      presentation() = 0;
virtual void        close(ConfigFile* cf) = 0;
virtual bool        fileexists(const String& path) = 0;
```
Реализация каталога (`ConfigStorage.cpp:39-93`):
- `readfile` — путь с `/` заменяется на `\`, файл читается `TFileStream` (`ConfigStorage.cpp:44-53`),
  возвращается `ConfigFile{str, addin=NULL}` (`ConfigStorage.h:20-24`), нет файла → `NULL`;
- `writefile` — `fmCreate` + копирование потока (`ConfigStorage.cpp:71-79`);
- `fileexists` — `FileExists(fdir + path)` (`ConfigStorage.cpp:88-93`);
- `presentation()` — путь каталога (`ConfigStorage.cpp:82-85`).
- Аналогичный адаптер для самого контейнера — `ConfigStorageCFFile` (`ConfigStorage.cpp:101-216`):
  `readfile` проходит вложенность, вызывая `f->GetCatalog()` (`ConfigStorage.cpp:127-155`),
  т.е. поддерживает путь `каталог/файл`.
- `container_file` (`ConfigStorage.h:84-101`) — обёртка элемента таблицы ИБ: распаковка
  (`ConfigStorage.cpp:244-312`), «сырой» поток (`ConfigStorage.cpp:315-353`), кэш `std::map` по имени.

Практический вывод: чтобы читать такой каталог, нужно повторить:
`readfile(path)` (нормализация `/`→`\`, чтение файла), рекурсивный обход каталогов,
и правило «текст модуля = `<GUID>.<N>/text`».

### 4.3. Настоящее хранилище (1CD с таблицами DEPOT)

- Признак: в БД есть таблицы `DEPOT`, `USERS`, `OBJECTS`, `VERSIONS`, `LABELS`, `HISTORY`,
  `LASTESTVERSIONS`; `is_depot = true` (`Class_1CD.cpp:8036-8078`).
- Версия хранилища — поле `DEPOT.DEPOTVER`: `03…`, `05…`, `06…`, `07…` → `depotVer3/5/6/7`
  (`Class_1CD.cpp:10240-10249`); для 6+ добавляются `DATAHASH` и упакованные данные
  `data/pack/pack-*.ind|pck` (`Class_1CD.cpp:10444-10497`).
- Номер версии: `get_ver_depot_config(ver)` — 0 = последняя, -1 = предпоследняя и т.д.,
  через `VERSIONS.VERNUM` и индекс PK (`Class_1CD.cpp:10004-10059`).
- Выгрузка: `save_depot_config(filename, ver)` (`Class_1CD.cpp:10112`) и
  `save_part_depot_config(filename, ver_begin, ver_end)` (`Class_1CD.cpp:10941`) собирают
  обычный `.cf`: создают `v8catalog(__filename, false)` (`Class_1CD.cpp:10516`), пишут
  `version` (`Class_1CD.cpp:10536-10558`), `root` (`Class_1CD.cpp:10560-10573`,
  `Class_1CD.cpp:10858-10882`), `versions` (`Class_1CD.cpp:10844-10856`, `10884-10902`) и файлы
  объектов через `createFile`/`WriteAndClose` (`Class_1CD.cpp:10905-10920`).
  Для формата 8.0 (версия < 100) файлы объектов дополнительно кладутся в каталог `metadata`
  (`Class_1CD.cpp:10905-10913`).
- Расширения из ИБ: `CONFIGCAS`/`CONFIGCASSAVE` + `configinfo` (§3.4), выгрузка —
  `Class_1CD.cpp:11911-11935`.

Чтобы поддержать этот режим, нужно повторить: чтение таблиц 1CD (`T_1CD`/`table`/`field`/`index`),
разбор `DEPOT.DEPOTVER`, `VERSIONS.VERNUM`, `HISTORY`/`EXTERNALS`, и сборку `.cf`
(`root`/`versions`/`version`) — это отдельный большой слой (у эталона ~12 тыс. строк `Class_1CD.cpp`),
не сводящийся к чтению контейнера.

- `.cf` — читается полноценно: `v8reader_cli.exe info "C:\work\cpp\utils\1Cv8_bp.cf"` →
  42 категории, 15 523 объекта, формат 1.6.
- `.cfu` — контейнер не распаковывается (в `V8Container` нет ветки «весь файл — deflate»);
  в эталоне это `APIcfBase.cpp:1052-1068`.
- `.cfe` — уже работает: `info YellowWatcher.cfe` → корневой GUID `0486e422-…`, имя `YellowWatcher`,
  синоним `Yellow watcher`, 14 категорий / 54 объекта (3 обработки, 5 отчётов, 12 справочников и т.д.).
  То есть `configinfo` уже разбирается (в `V8Text` появился `V8Text::parseSequence`,
  `V8Text.cpp:533`), ветка `configinfo` — `ConfigurationReader.cpp:436-448`.
- `.epf` — определяются корневой GUID, имя/синоним/комментарий, формы (32), макеты (106) и модуль
  объекта (`<descriptor UID>.0/text`); но состав реквизитов/ТЧ/команд интерпретируется неверно
  (см. п. 5 ниже): у `bddRunner.epf` 120 реквизитов выгружаются как «Команды».
- `.erf` — не проверялся (нет образца).
- каталог-«хранилище» (`SourceCF`-подобный) и 1CD-хранилище (`DEPOT`) — не поддерживаются.

Рекомендации по приоритету:

1. **Исправить таблицу GUID→вид раздела** в `MetadataCatalog.cpp:85-118` (`kSectionTableGuids`).
   Сейчас неверно: `2bcef0d1…` помечен `Attributes` (`MetadataCatalog.cpp:97`), хотя это
   **табличные части**; `ec6bb5e5…` помечен `Commands` (`MetadataCatalog.cpp:99`), хотя это
   **реквизиты**. Проверка на реальном файле: `bddRunner.epf`, таблица `ec6bb5e5…` (120 элементов)
   содержит записи вида `{{0,{27,{2,{3,{1,0,guid},"DebugLog",…}}}},0}` — это реквизиты, но в
   `composition.txt` они выведены как «Команды». Правильно:
   `2bcef0d1…` = TabularSections, `3daea016…` = Templates, `d5b0e5ed…` = Forms,
   `ec6bb5e5…` = Attributes, `45556acb…` = Commands (может отсутствовать — как в обоих `.epf`).
   `d5b0e5ed…`/`ec6bb5e5…`/`45556acb…` выведены из индексов эталона
   (`DataProcessors.cpp:10-24`: `tabIdx=3`, `moxIdx=4`, `cmdIdx=5`, `formsIdx=6`, `attIdx=7`)
   и подтверждены дампами (`props[4]` = первая форма из `d5b0e5ed…`).
2. **Не полагаться на индексы таблиц** (`layoutForCategory`): у `.epf` порядок таблиц другой
   (см. таблицу в §2.3), а таблица команд может отсутствовать. Определять раздел по GUID таблицы,
   индексы — только как fallback.
3. **`.cfu`**: добавить в `V8Container::open` попытку inflate всего файла (как
   `APIcfBase.cpp:1052-1068`) и повторное открытие как контейнера 1.5/1.6.
4. **`.epf/.erf` — ClassId и тип**: брать ClassId из обёртки `{1,{self},1,{ClassId,body}}`
   (`c3831ec8…` = ExternalDataProcessor) и определять `ExternalProcessing`/`ExternalReport`
   по нему, а расширение использовать как подсказку. Это позволит корректно открывать `.erf`
   с «чужим» расширением. Значение ClassId для `ExternalReport` нужно подтвердить на реальном
   `.erf` (в проверенных файлах его нет).
5. **Разделять `elementName` (имя элемента контейнера) и `objectUid` (GUID из дескриптора)**.
   Сейчас в списке объектов `.epf` показывается UID `72a612b7…`, тогда как элемент контейнера и
   `root` — `433e4fdb…`; обе величины нужны: `elementName` — для чтения файла объекта,
   `objectUid` — для поиска контейнеров модулей (`<objectUid>.N`). См.
   `ConfigurationReader.cpp` (`buildExternalObject`, `descriptorFor`) и `ModuleExtractor.cpp:78-129`.
6. **Проверка дескриптора**: `descriptorFor`/`findFirstDescriptor`
   (`ConfigurationReader.cpp:164`, `ConfigurationReader.cpp:859`) должны требовать:
   `[kind:int 1..20, [flag:int, ?, guid], "Имя":string, {локализация}, "Комментарий"]`,
   чтобы «тело объекта» `{1,<props>,N,<tables>}` не принималось за дескриптор
   (иначе имя = «4», синоним = «0» — так было до последней правки).
7. **Регрессионные тесты на эталонных файлах** (ожидаемые значения из этой проверки):
   - `UI_Portable.epf`: `root` = `433e4fdb-ede4-4263-bd7b-a306d3fac8f9`, UID = `72a612b7-6b1c-43ed-8f1a-7ff5ae4c19b8`,
     ClassId = `c3831ec8-d8d5-4f93-8a22-f9bfae07327f`, имя `УИ_ПортативныеУниверсальныеИнструменты`,
     синоним `Портативные универсальные инструменты`, комментарий `26.5.1`, макеты 106, формы 32,
     реквизиты 0, ТЧ 0, команд нет; модуль объекта = `72a612b7-….0/text` (36 845 Б);
   - `bddRunner.epf`: `root` = `c15bf2f2-272d-4fe6-a321-0d77e353c1ab`, UID = `fcd4c9b7-5f30-4115-afa3-5ddd71a1c140`,
     имя `bddRunner`, 3 макета, 9 форм, **120 реквизитов**, `copyinfo` = 87 объектов;
   - `YellowWatcher.cfe`: `configinfo[1][1]` = `0486e422-ae70-44b4-8b58-e7952ce247b8`,
     имя `YellowWatcher`, синоним `Yellow watcher`, версия `1.0.0.8`/`80315`,
     14 категорий / 54 объекта, 214 файлов в карте SHA-1;
   - `1Cv8_bp.cf`: 42 категории, 15 523 объекта (не должно измениться).
8. **Каталог-«хранилище»**: реализовать чтение распакованного каталога
   (`SourceCF`-подобного) по образцу `ConfigStorageDirectory` (`ConfigStorage.cpp:30-93`) и
   `ModuleTextStorage.cpp:183-260`: `readfile(path)` с нормализацией `/`→`\`, рекурсивный обход
   каталогов, текст модуля — `<GUID>.<N>/text`. Настоящее 1CD-хранилище (`DEPOT`) — отдельный
   крупный этап (§4.3), после `.erf`/`.cfu`.
9. **Мелкие, но важные нюансы**:
   - `versions` = `{1, элементов+1, "", uid, имя, uid, …}` (`guids.h:1592`) — не считать, что
     count равен числу элементов;
   - имена элементов контейнера ищутся без учёта регистра (`APIcfBase.cpp:239`), GUID-ы — нижний регистр;
   - 1.6-контейнер требует смещения `0x1359` при чтении блоков (`v8_constants.h:19`);
   - `copyinfo` (`.epf/.erf`) — готовый справочник `uid → (ClassId,"Имя")` плюс связи
     «объект→родитель»; удобен для быстрой проверки/заголовков, но состав всё равно читать из
     тела объекта (в эталоне не используется вовсе).
