# Тестовая база контролов управляемых форм

База нужна, чтобы сверять вид каждого контрола управляемой формы с
конфигуратором не на одной форме «Авансового отчёта», а на наборе форм,
которые мы сами создаём и меняем. Исходники базы лежат в репозитории, сама
база — одноразовый артефакт на машине разработчика.

## Что где лежит

| Что | Где |
|---|---|
| Скелет пустой конфигурации, снятый платформой | `tests/fixtures/controlbase/skeleton` |
| Спецификация форм и контролов | `tests/fixtures/controlbase/spec/controls.json` |
| Выгрузка конфигурации в файлы (фикстура) | `tests/fixtures/controlbase/ConfigFiles` |
| Контейнер для просмотрщика | `tests/fixtures/controlbase/1Cv8_controls.cf` |
| Эталоны из конфигуратора | `tests/fixtures/controlbase/refs` |
| Базовый уровень текстовых расхождений | `tests/fixtures/controlbase/baseline.json` |
| Словарь тегов и свойств по корпусу БП | `tests/fixtures/controlbase/vocab.json` |
| Матрица покрытия контролов | `docs/controls-matrix.md` |
| Файловая информационная база | `E:\work\1cv83.db\qtv8db` (по умолчанию) |

Конфигурация называется «Контролы управляемых форм», в ней одна обработка
`Контролы`, а в ней — по форме на семейство контролов: `ПоляВвода`,
`Надписи`, `Группы`, `Кнопки`, `ГруппаКнопок`, `Страницы`, `Таблица`,
`Заголовок` (собственный Title формы и панель без автозаполнения),
`КоманднаяПанель` (своя панель с кнопкой), `Меню` (два подменю в полосе),
`Картинки` (декорации-картинки), `Колонки` (группа колонок таблицы),
`Переключатели` (список выбора и тумблер). Формы описаны реквизитами самой
формы: так поля и таблицы получают настоящие типы без объектов-носителей.
Заголовок формы и свойства автопанели задаются в спецификации ключами `props`
и `autoCommandBar`.

## Конвейер

```
spec/controls.json ──► control_base.py build ──► база qtv8db ──► 1Cv8_controls.cf
                                   │                 │
                                   └── платформа нормализует выгрузку (pull)
                                                     │
                       конфигуратор: control_refs.py capture ──► refs/<форма>.png
                                                     │
   v8reader_cli form-model + headless Chrome: control_compare.py ──► out/control/**
```

### 1. Собрать базу и контейнер

```powershell
python tools/control_base.py build
```

Команда генерирует выгрузку из спецификации, создаёт базу (если её нет),
загружает конфигурацию (`/LoadConfigFromFiles` + `/UpdateDBCfg`), **забирает
нормализованную выгрузку обратно** (`/DumpConfigToFiles`) и сохраняет
контейнер (`/DumpCfg`). Обратный дамп важен: платформа сама дописывает
служебные элементы (контекстное меню, расширенную подсказку), переставляет
свойства в порядке схемы и считает хеши — фикстурой становится именно он.

Платформа берётся из спецификации (`"platform": "8.3.27.2342"`): эталоны
снимаются той же версией, иначе вид контролов не совпадёт.

### 2. Снять эталоны из конфигуратора

```powershell
python tools/control_refs.py capture --all
python tools/control_refs.py capture --form ПоляВвода
python tools/control_refs.py list
```

Скрипт запускает конфигуратор, для каждой формы находит её фильтром дерева,
открывает, ждёт синюю рамку полотна предпросмотра (цвет `#1E90FF`, 2 px),
обрезает ровно по внутреннему краю и сохраняет PNG с манифестом (размер,
хеш, дата). Захват идёт в интерактивном сеансе на экране 1920×1080 с
развёрнутым окном конфигуратора; если раскладка другая, поправьте координаты
в `refs/ui.json` (скрипт перезаписывает его при каждом запуске) или ключом
`--calibration`.

### 3. Сверить наш рендер с эталоном

```powershell
python tools/control_compare.py --all
```

Для каждой формы собирается модель (`v8reader_cli form-model`), снимается
страница рендерера в размере эталона и считается расхождение. Пиксели делятся
на **структурные** (рамки, линии, заливки, значки) и **текстовые** (края
глифов: GDI платформы и DirectWrite в Chromium расходятся принципиально).
Результат — `out/control/<форма>/{ref,ours,diff,pair}.png`, сводка —
`out/control/control-report.md`. Ключ `--update-baseline` фиксирует текущий
уровень текстовых расхождений в `baseline.json`.

Снимок делается в рамке фиксированного размера (`_shot.html` + `iframe`), а не
прямо со страницей: флаг `--window-size` задаёт размер *окна*, и Chrome на
Windows не даёт окну стать уже ~500 px. С эталоном 342×189 область просмотра
выходила 500×189, снимок обрезался слева до 342, и всё правое — кнопка
автопанели «Ещё» — уезжало за кадр: каждая форма теряла на этом ~360 px.
Проверка — `out/preview/_ruler.html`: вне рамки маркер `right:0` в снимок не
попадает, в рамке 342×189 попадает на x=332…341.

Приёмка по контролу: **структура 0**, текст не выше базового уровня.

### 4. Гейт модели (без 1С и без Chrome)

```powershell
python tools/control_fixture_check.py --cli out/mingw/v8reader_cli.exe
```

Сравнивает JSON-модель каждой формы фикстуры с её `Ext/Form.xml`: теги, имена,
порядок и значения свойств. Это же проверяется в `ctest` (`control_fixtures`),
поэтому потери свойств при разборе контейнера ловятся в обычном CI. Скрипт
сам ставит в `PATH` библиотеки Qt: без них `v8reader_cli` не стартует, а гейт
молча сообщал «form-model: » на каждой форме.

## Как добавить контрол

1. Дописать форму или элемент в `spec/controls.json` (теги и свойства — как в
   `Form.xml`, значения: строка/число/`{"title": "..."}`, для записи, которой
   нет в словаре свойств, — `{"xml": "<Picture>…</Picture>"}`). Кнопке нужна
   команда формы: секция `"commands": [{"name": ..., "title": ...}]` у формы и
   `"CommandName": "Form.Command.<имя>"` у кнопки — без команды конфигуратор
   кнопку не рисует вовсе. `ButtonGroup` и `Popup` рисуются только внутри
   `CommandBar` (вне полосы платформа их просто не показывает).
2. `python tools/control_base.py build` — платформа проверит выгрузку; ошибки
   печатаются из журнала `/Out`. Ошибка XDTO называет файл формы — дальше
   виновата либо запись через `{"xml": …}`, либо свойство, взятое из
   `vocab.json` «по большинству»: словарь собирается по корпусу и иногда
   приписывает тегу чужое свойство (`Border` у `PictureDecoration`).
3. `python tools/control_refs.py capture --form <форма>`.
4. `python tools/control_compare.py --form <форма>` — посмотреть дифф и
   `pair.png`.
5. Править модель (`FormWebModel.cpp`, `FormReader.cpp`) или рендерер
   (`resources/formpreview/js/form-preview.js`, `qv8-host.css`) до
   структурного нуля, затем `--update-baseline`.

## Текущее состояние

Тринадцать форм: `ПоляВвода`, `Надписи`, `Группы`, `Кнопки`, `ГруппаКнопок`,
`Страницы`, `Таблица`, `Заголовок`, `КоманднаяПанель`, `Меню`, `Картинки`,
`Колонки`, `Переключатели`. Эталоны сняты у всех, сверка работает, базовый
уровень расхождений (пара «структура/текст» на форму) записан в
`baseline.json`. Покрытие по тегам и очередь следующих контролов — в
`docs/controls-matrix.md` (`python tools/control_matrix.py --write`).

Что уже выяснено замерами (и закрыто или поставлено в очередь):

- **Заголовок окна = собственный `Title` формы.** Форма «Заголовок»
  (`Title` + `AutoTitle=false`) рисует в полоске «Заголовок из формы», формы
  без своего `Title` — пустую полоску: конфигуратор не подставляет синоним
  объекта. Модель теперь отдаёт `Title`/`AutoTitle` только из формы, и полоса
  перестала расходиться на ~1 000 px у каждой формы.
- **«Ещё» у панели с автозаполнением.** Форма без своего `Autofill=false`
  получает полосу с одной кнопкой «Ещё»; «Заголовок» с `Autofill=false` —
  без неё. Рендерер выбрасывал пустую панель целиком, и строки уезжали на её
  высоту; теперь полоса остаётся в раскладке, и первая строка полей встаёт на
  ту же высоту, что в эталоне (y=60).
- **Шаг строк в листовой вертикальной группе = Single (9).** У платформы
  строка поля в 25 px идёт через 34 px: «ПоляВвода» — рамки на y=60, 94, 128;
  у нас было 60, 88, 116 (зазор 3 px вместо 9, шаг 28). Правило `applyLayout`
  ставило Single только «компактным» группам ровно из двух контролов, а
  остальные падали в CSS-запас 3 px. Теперь вертикальная группа, все дети
  которой — обычные контролы (без вложенных групп), получает Single. Форма
  «ПоляВвода»: структура 2 177 → **406** px; зазор на картинке
  `out/control/ПоляВвода/pair.png` совпал построчно.
- **Команды формы — то, без чего кнопки не рисуются.** Конфигуратор не
  показывает ни кнопку в обычной группе, ни кнопку своей командной панели без
  команды: у формы с кнопками полотно было 89×70 — только полоса. Теперь у
  форм «Кнопки», «ГруппаКнопок» и «КоманднаяПанель» есть `Commands` с
  `Action`, кнопки ссылаются на них через `CommandName` = `Form.Command.<имя>`,
  а в выгрузку пишется модуль формы с обработчиками. Кнопки появились:
  «Кнопки» 154×133, «КоманднаяПанель» 173×122. Кнопка в `ButtonGroup` не
  рисуется и с командой — «ГруппаКнопок» так и осталась 89×70; причина не
  выяснена, это следующий замер.
- **Таблица** — самый большой структурный разрыв (≈11,6 тыс. px): шапка,
  колонки и рамка. Следующий шаг после кнопок.
- **Полоса команд была на 5 px выше платформенной — снята.** Эталон: кнопка
  «Ещё» y=24…50, полоса 23…50 (27 px). Наша оболочка `.fp-item` добавляла по
  1 px рамки и отступа сверху и снизу, а полоса — ещё 1 px нижнего отступа:
  21…53 (32 px). Снял ровно два нижних пикселя (нижний отступ полосы и нижний
  padding оболочки); верхние смещения, которые ставят кнопку на 24, не
  тронуты. Полоса стала 30 px = 2 px отступа + 27 px полосы + 1 px рамки, и
  следующий корневой ряд встаёт на y=60 сам, без отрицательных margin.
  «Кнопки»: 18,00 % → **6,10 %** (структура 2 997 → 575, осталось только
  начертание глифов), «Страницы» 7,09 % → **2,97 %** (2 047 → 459).
- **Вертикальный стек кнопок идёт шагом 36 px.** Эталон «Кнопок»: рамки
  60…85 и 96…121, шаг 27 + 9. Наши строки были 30 px (оболочка 2 px) с
  зазором 3 px (CSS-запас) — шаг 33, кнопка на 2 px ниже, кнопка шире
  полотна → полоса прокрутки. Теперь строка кнопки 27 px,
  `leafOnlyVerticalStack` распространяется и на кнопки, кнопка растягивается
  на ширину группы и центрирует подпись, как платформа. «КоманднаяПанель»
  13,97 % → 13,56 % (там своя панель, её шаг — следующий замер).
- **Заголовок группы — 1 px под её верхом.** Подпись раздела тянулась на
  1 px вверх (`margin-top: -1px`) как компенсация тех же 2 px полосы. Теперь
  `margin-top: 1px`, `margin-bottom: 3px`: чернила на строках 63…77, первая
  строка на 82 — ровно как в эталонах «Группы» и «Надписи». «Группы»
  7,46 % → 6,91 %, «Надписи» 8,57 % → 8,36 %.
- **«Надписи»: полосы прокрутки из ничего — сняты.** Контент выходил за
  полотно на 5 px (119 при 114) — включалась вертикальная дорожка, она
  сужала область до 353 px, и `fp-labelfield-value` (260 px) переставал
  влезать. Виноват ряд `LabelField`: общий минимум `.fp-control-wrap` 22 px
  делал текстовую строку «Поле-надпись:» шестью пикселями выше
  платформенной. У titled-LabelField минимум теперь 16 px (сама текстовая
  строка); рядом с редактором высоту и так задаёт редактор. 8,36 % → 3,80 %
  (4 047 → 1 769).
- **Своя командная панель — тоже одна полоса 27 px.** Оболочка элемента
  (1 px рамки и 1 px отступа со всех сторон) плюс собственный нижний отступ
  полосы 4 px давали строку 35 px: кнопка «Кнопка панели» рисовалась на
  62…88 и начиналась с x=14, а платформа ставит её на 60…86 с x=10.
  «КоманднаяПанель» 13,56 % → 8,18 % (1 777 → 654). Остаток — подпись «Своя
  командная панель»: она получается на 5 % шире платформенной из-за
  начертания, переносится на вторую строку и снова включает дорожку.
- **Ширина поля: эталон 304 px, у нас 208 — и это не растягивание, а вид
  поля.** В «Группах» поле «Строка» (Width 20 символов) у платформы растянуто
  на всю ширину группы (x 61…364), у нас стоит по authored-ширине (x 65…272).
  Причина не в `HorizontalStretch` (он по умолчанию включён и у нас): 1C
  отдаёт текстовому полю всю дорожку значения вертикальной группы, поэтому
  authored `Width` — предпочтительный размер, а не предел. Проверено тремя
  формами: «Группы» (Строка 20 в группе 355 px → 306), «ПоляВвода» (та же
  Строка 25 рядом с Число 15 и Дата 15: 259 остаются 259, а 182 остаются 182)
  и «Страницы» (Строка 20 внутри `Page` — 208 из 283, страница раскладывает
  детей по их размерам). Отсюда правило: текстовый/ссылочный реквизит с
  authored `Width` без `MaxWidth` в вертикальной группе (не `Page`) тянет
  дорожку на себя, числа и даты держат authored ширину. База флекса — не
  презентационный слот (25 символов = 200), а painted-полоса (авторские
  10·n+10), иначе поле, которому дорожки хватает ровно, теряет 1 px справа.
  «Группы» 2 664 → **2 478**, «ПоляВвода» 450 → 450, большая форма 8 634 px
  (2,00 %) не сдвинулась: в «АвансовомОтчёте» ни одно поле с authored `Width`
  не лежит прямо в вертикальной группе.
  Остаток — колонка подписи: рамка поля начинается на x=65 против 61 у
  платформы, потому что наша подпись «Строка:» на 1 px шире GDI-шной, а зазор
  между подписью и полем у платформы в этой группе 0 вместо наших 5.
- **Геометрия DOM как инструмент: `tools/form_view_probe.py`.** Пиксельная
  сверка говорит «где», но не «почему»: по рамке не видно, какой узел получил
  ширину и какой класс растягивания ему выставили. Проба рендерит ту же
  страницу в iframe нужного размера и вытаскивает из живого DOM
  прямоугольники узлов, их классы и `data-fp-*`-решения. Именно она показала,
  что оболочка поля уже во всю группу (356 px), а внутри `.fp-field-row`
  редактор запинен на 210 — то есть чинить надо не контейнер, а признак
  растягивания у поля. Работает без интерактивного сеанса 1С.
- **Шаг до вложенной группы: обычная строка отдаёт Single 9 px, а не 3 + 4.**
  Поле прямо в вертикальной группе, за которым идёт голая горизонтальная
  группа, у платформы идёт обычным шагом Single. У нас работал CSS-хвост
  `margin-top: 4px` поверх компактного `row-gap: 3px` — 7 px вместо 9, и вся
  группа «Число/Дата» стояла на 2 px выше эталона вместе со своими рамками.
  Правка — один `margin-top: 6px` в `viewer.css`: «Группы» 2 478 → **1 295**,
  ни одна из восьми остальных форм и «АвансовыйОтчёт» не сдвинулись.
- **Подпись окна — 12.2 px, а не 13.** Полоса заголовка окна над командной
  панелью (`.fp-form-title`, цвет неактивного заголовка `#99b4d1`) рисовала
  подпись 13 px: в «Заголовке» чернила «Заголовка из формы» выходили x 5…138,
  y 5…17 при эталонных x 2…126, y 5…15. Теперь подпись совпадает с эталоном
  до пикселя (x 2…126, y 5…15): 12.2 px, `padding: 1px 1px 2px`. «Заголовок»
  1 799 → **1 656**.
- **Где предел этой метрики: длинные слова и заливки.** «Структура» в отчёте —
  это пиксели, не попавшие в мелкие связные компоненты «чернил» эталона
  (≤420 px, ≤24 в высоту, ≤60 в ширину). Слово шире 60 px в этот фильтр не
  проходит, поэтому расхождение по нему целиком уходит в «структуру», хотя это
  растеризация: ClearType платформы против сглаживания Chrome. Так устроены
  все оставшиеся полосы «Надписей» (1 660) и «Кнопок» (в жёлтой кнопке вся
  внутренность — одна связная заливка). Проверка, которая отличает это от
  вёрстки, — чернильные рамки по полосам: в «Надписях» они совпадают с
  эталоном до 1 px (11…69 против 12…70, 10…126 против 10…127), в
  «АвансовомОтчёте» рамки полей строки «Подотчетное лицо» совпадают точно
  (98…122, 114…637, разделители кнопок 481/502/523). Гоняться за такими
  полосами не надо: это не раскладка.
- **Таблица: своя панель не показывалась вовсе.** Модель веб-рендера
  подставляла таблице `CommandBarLocation=None`, если её путь к данным
  совпадал с главным реквизитом формы: «у основной таблицы списка своей панели
  нет». Для формы списка документа это верно (там команды уходят в панель
  формы), но таблица значений на форме обработки свою панель сохраняет —
  эталон «Таблица» 443×529 держит на ней «Добавить», стрелки перемещения,
  «Поиск (Ctrl+F)» и «Ещё». Теперь подстановка включается только когда главный
  реквизит — динамический список (`mainAttributeIsDynamicList` в
  `FormWebModel.cpp`), «АвансовыйОтчёт» не сдвинулся (8 634 px, 2,00 %).
  Заодно: корневая таблица больше не сдвигается на 2 px вниз и 1 px вправо
  оболочкой элемента, а рендер сам добавляет строку поиска в панель таблицы,
  когда форма её не описывает. 11,35 % → **9,52 %** (12 004 → 9 990).
  Остаток: строка фильтра «Поле1: Значение1» / «Поле2: Значение2» на эталоне —
  это подсказка конфигуратора, настоящая форма её не рисует, поэтому
  догонять её не надо; и заглушка «Поиск (Ctrl+F)» внутри поля поиска.
- **Тип реквизита формы не доезжал до рендерера: «Дата» сравнивалась как
  латиница.** `describeType` в `FormOwner.cpp` распознавала «Булево», «Дата»,
  «ДатаВремя» и «Время» через `QLatin1String("…")`, а в UTF-8 исходнике
  кириллица — многобайтные символы: `QLatin1String` читает каждый байт как
  отдельный символ, и сравнение с `QString` не совпадает никогда. В модели
  реквизит оставался с типом «Дата», рендерер такого типа не знает — поле
  даты рисовалось как текст: без маски, без кнопки календаря и без учёта
  authored-ширины (в «Группах» рамка 130 px вместо 152). Теперь сравнение идёт
  `QStringLiteral`, а вид даты (`Date`/`DateTime`/`Time`) пишется в модель
  рядом с типом: `buildAttribute` раньше отдавал пустой `dateFraction`.
- **Квалификаторы типа из бинарной формы терялись на разборе.** Разбор
  `typeHintFromAttributes` определял только вид значения («Строка», «Число»,
  «Дата»), а числа за кодом типа — длину строки (`["S", 40]`) и разрядность
  (`["N", 10, 2]`) — выбрасывал. Из-за этого модель не знала ни длины строки,
  ни дробной части числа: ширина поля по умолчанию и кнопка калькулятора
  опираться было не на что. Теперь подсказка типа приходит с квалификаторами
  («Строка(40)», «Число(10,2)»), а `buildAttribute` пишет `stringLen` и
  `numberQ` в модель. Гейт фикстуры проходит: 9 форм, расхождений модели с
  `Form.xml` нет.
- **Кнопки редактора: календарь и калькулятор — это 21 px + 1 px разделителя.**
  Замер по эталонам: рамка поля = authored-ширина в знаках (10 px/знак) + 11 px
  вставки + 21 px на каждую кнопку. «Дата» (12 знаков) в «Группах» — 152 px
  (120 + 11 + 21), «Число(10,2)» и «Дата» в «ПоляВвода» (15 знаков) — 182 px у
  обоих, «Строка(25)» — 261 px. У числа кнопка-**калькулятор** есть только при
  дробной части: `Число(8,0)` в «Группах» её не получает (111 px), а
  `Число(10,2)` — получает. Картина «до» и «после» на `out/control/ПоляВвода`:
  обе кнопки появились в нужных местах.
  Ценой стало то, что новые кнопки встали на 1–3 px вбок (сдвиг начинается с
  подписи: наши подписи шире платформенных на 2–4 px), поэтому пиксельный счёт
  «ПоляВвода» подрос (406 → 450). Это плата за настоящую геометрию поля, а не
  за пустое место: до правки календаря и калькулятора на формах не было вовсе.
  Кнопка дробного числа — платформенная картинка «Калькулятор»
  (`StdPicture.Calculator`), а не «…» выбора значения: значок в эталоне 9×11 px,
  наш совпадает с ним по размеру и форме и расходится на 1–2 px позиции вместе
  со всей рамкой поля.
- **Подпись группы: 16 px — на 4 px шире платформенной, и это 15.5 px.**
  Строка «Вертикальная группа» в «Группах»: эталон — чернила на x=11…163
  (153 px), у нас при 16 px — 11…167 (157 px): продвижения глифов в Chrome на
  те же ~3 % шире GDI. Замер канвы дал точное попадание на 15.5 px (153.0 px до
  знака). После правки чернила 11…162 на тех же строках 63…77; отступы и цвет
  (`#009646`) не двигались. «Группы» 2 816 → **2 664**, «Надписи» 1 769 →
  **1 660**, а большая форма вернулась к базовой линии (8 713 → **8 634**).
  Заголовки страниц и вкладок правило не трогает — они рисуются другими
  классами.
- **Масштаб базового шрифта: 13 px — единственный, что держит настоящую
  форму.** Подписи в наших формах шире платформенных на 2–4 px («Строка:» —
  47 против 43), это сдвигает вправо и колонку подписи, и редактор. Проверил
  базу шрифта как общий множитель: `.fp-root { font-size: 12.5px }` уменьшает
  девять форм на 184 px, но «АвансовыйОтчёт» при этом разваливается на
  2 464 px (2,58 %): его строки и переносы свёрстаны под 13 px. 12 px тоже хуже.
  Откат — база остаётся 13 px, точечно уменьшена только подпись группы (выше).
  Расхождение подписей — растеризация GDI: платформа округляет продвижения
  глифов до целых пикселей, Chrome — нет.

- **Декорация-картинка из библиотеки платформы рисуется 16 px и без
  authored-размера.** Рендерер нарочно гасил такую декорацию (класс
  `fp-unpainted-picture` → 0×0): «раз размера не задали, платформа ничего не
  отводит». Эталон «Картинки» показал обратное — три декорации в группе дают
  чернила 82…97, 107…122, 133…146: коробка ровно 16 px, шаг Single 9 (25).
  Причин было две, и обе в коде: `StdPicture.Print` не было в таблице
  `STD_PICTURE_RU` (файл `Pechat.png` при этом лежал в `std-pictures/`), а
  страховка от пустых декораций гасила заодно и те, что мы умеем рисовать.
  Теперь ноль остаётся только для ссылок, которых в библиотеке нет, а у
  известных появился класс `fp-picture-library16`: 16×16 без обвязки контрола —
  её минимум 22 px и 2 px отступов с рамками растягивали строку до 26 и шаг до
  35. «Картинки»: структура **0** (все три картинки совпали попиксельно).
- **`Border` у `PictureDecoration` платформа не принимает.** Загрузка падает
  XDTO-исключением на форме целиком, а в `vocab.json` свойство значилось — это
  ложное попадание словаря: в 3001 форме корпуса `<Border>` у
  `PictureDecoration` не встречается ни раза. Спецификация исправлена; такие
  «свойства из словаря» проверяются загрузкой, а не доверием к списку.
- **Полоса команд: фантомные 7 px ломали узкие формы.** У полосы `gap: 7px`,
  справа «Ещё» с `margin-left: auto`, между ними нулевая `.fp-bar-spacer`.
  Пока места хватает, шаг съедает авто-отступ; в узкой форме (93 px
  «Картинки», 89 px «ГруппаКнопок») минимальная ширина полосы выходила на 4 px
  больше колонки, кнопка выезжала за правый край и подрезалась — рамка 18…74
  вместо платформенных 14…74. Лечится минусом того же шага у распорки: в
  широкой полосе его по-прежнему съедает авто-отступ, в узкой кнопка встаёт по
  краю колонки. «Картинки» структура 126 → **0**, «ГруппаКнопок» 452 → 129.
- **`ButtonGroup` и `Popup` вне полосы команд платформа не рисует вовсе.**
  Открытый вопрос с круга кнопок («кнопка в ButtonGroup не видна и с
  командой») закрыт: дело не в `CommandName` и не в `Type`, а в месте — группа
  кнопок и подменю живут только внутри `CommandBar`. Фикстура перестроена:
  `ГруппаКнопок` и `Меню` держат элементы в полосе, эталоны выросли с 89×70
  (пустая форма) до 179×97 (две кнопки рядом) и 246×97 (два подменю).
  «ГруппаКнопок» 383 → **129**, «Меню» — 241.
- **Подписи списка выбора теперь доезжают до модели.** В записи формы подпись
  переключателя лежит ссылкой на значение — `("#", GUID, {0, 1, {S, «Первый»},
  …})`, — а `collectLocalizedDeep` ищет заголовок в виде `{1, 1, {ru, текст}}`
  и такое значение не находил: `choiceItems` оставался пустым, и рендерер
  рисовал вместо подписей «<Значение 1>». Добавлен сбор типизированного
  значения (`S`/`N`/`B`); «Переключатели» получили «Первый, Второй, Третий».
  Вид переключателя тоже доехал: он лежит седьмым полем блока `{8, …}`, а не
  внутри его записи (там количество элементов списка) — 0 Auto, 1
  RadioButtons, 2 Tumbler. Сверено по форме «Ввод начальных
  остатков/ФормаАрендаЛизинг», где Tumbler и Auto стоят рядом, по нашим двум
  переключателям и 9 переключателям корпуса; гейт фикстуры по «Переключателям»

  выходит выше платформенной: 2 357 px структуры — следующий замер.
- **`ColumnGroup` с `ShowInHeader`: дети идут вертикально.** Эталон «Колонки»:

## Ограничения

- Захват эталонов требует интерактивного сеанса Windows с конфигуратором;
  1С-независимый гейт (`control_fixture_check.py`) работает где угодно.
- Эталоны зависят от платформы: версия записана в `refs/manifest.json`.
- Данные в контейнере беднее выгрузки, поэтому «полное совпадение» по
  свойствам возможно только у фикстуры, которую мы сами задаём.
